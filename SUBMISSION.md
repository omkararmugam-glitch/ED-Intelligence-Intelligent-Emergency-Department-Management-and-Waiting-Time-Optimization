# ED Intelligence — submission

## What this is

1. **One pipeline, three usually-separate problems.** It forecasts how many patients
   will arrive each hour, predicts how long an individual patient will wait, and
   searches for the cheapest doctor roster that still meets a waiting target — and the
   forecast feeds the simulation, which feeds the roster search.
2. **The checks that usually go missing are first-class.** A simulation that cannot
   reproduce its own dataset is *refused* a staffing plan rather than asked politely;
   subgroup fairness is measured with intervals; the value of queue features is
   isolated by a controlled ablation instead of assumed.
3. **Every interval is calibrated against held-out data**, with rolling conformal
   recalibration measured against a static split rather than trusted.
4. **It runs end to end on a laptop** — 16 stages, double-click to demo, a FastAPI
   service and a Streamlit dashboard, all from the same artifacts.
5. **The limits are stated as loudly as the results.** The data is synthetic, the
   staffing finding is partly circular, one learned policy is a negative result, and
   none of it is evidence about a real department.

**Decision support only.** Every number here is an estimate for a clinician or manager
to weigh. Nothing triages a patient or makes an autonomous clinical decision.

**All data is synthetic**, generated by `scripts/original_generator/generate_ed_data.py`
with parameters chosen to sit inside published benchmark ranges. No real patient data
was used, downloaded or touched.

## How to run

### 0. Double-click `Setup.cmd` — only needed on a new machine

It finds Python 3.12, creates `.venv` and installs the pinned dependencies from prebuilt
wheels. A few minutes, once. It ends with `Setup complete. Double-click Start-Demo.cmd.`

Skip this if `.venv` already exists. If you skip it and it was needed, `Start-Demo.cmd`
says so rather than failing obscurely.

### 1. Double-click `Start-Demo.cmd`

That is the whole of it. No terminal, no commands, no arguments.

It checks the environment, starts the API and the dashboard, waits for both to come up
and opens the browser.

**Double-click `Stop-Demo.cmd`** to shut it down.

```
Dashboard: http://localhost:8501   API docs: http://localhost:8000/docs
```

**The dashboard opens on the Command center**, which needs no clicks: expected arrivals
for the next 24 hours, the busiest hour, the typical ESI 3 wait, the congestion read for
the next 6 hours, the arrivals chart and what the service suggests.

**The model headline numbers are one click away, not on the Command center.** Wait-time
MAE **11.52 min against 34.23** for the baseline, conformal coverage **0.8875 rolling
against 0.849** static, arrivals forecast MAE **2.356 /h against 2.979** for
seasonal-naive, and the cheapest feasible roster **3 / 3 / 2 / 2 at 49,280** are on the
**Quality and equity** and **Research results** pages, both under *Clinical
intelligence* in the sidebar. The Command center answers "where is the department
now"; those two pages answer "how good is this, and where does it fail".

Both services bind to `127.0.0.1` and are reachable from that machine only; neither
authenticates, so neither should be published.

If the launcher refuses, the message says what to do. It refuses in three cases:
something other than a healthy ED API is holding port 8000 — it names the port, the
owner and the reason, and never kills it; `artifacts\` holds no trained models — it
names the single command that builds them; or `.venv` is missing — it names
`.\scripts\setup.ps1`. If the dashboard is already answering, which is what the Docker
stack or a second double-click looks like, it opens the browser and starts nothing.

Logs are in `runs\logs\api.log` and `runs\logs\app.log`. `Stop-Demo.cmd` stops only the
processes recorded in `runs\demo.pids`, after checking each is still the one recorded,
and never touches Docker.

### 2. Manual start

The same two services with their output in front of you, which is what you want if
something is misbehaving.

```powershell
.\scripts\run_api.ps1               # terminal 1: API on 127.0.0.1:8000
.\scripts\run_app.ps1               # terminal 2: dashboard on 127.0.0.1:8501
```

### 3. In Docker

```powershell
.\scripts\docker_up.ps1 -Open       # or double-click start_docker.bat
.\scripts\docker_down.ps1
```

The container runs as a non-root user and publishes only to `127.0.0.1`.

## What to look at first

The dashboard is a clinical-operations interface for the fictional **Northfield
General Hospital — Emergency Department**, with eleven pages in four groups. Every
page carries the banner *"Synthetic data. Decision support only, not for clinical
use."*

**A five-minute path through it:**

1. **Command center** (opens by default) — six figures with their change against the
   same hour last week, the arrivals forecast against its seasonal-naive baseline,
   the acuity mix, waits by acuity against the 30-minute target, a day-by-hour

   confidence interval. These use the simulation that *passed* validation; the

5. **Quality and equity** — where the model is weakest, including the high-acuity
   failure it reports about itself.

## Headline results

On `data/raw/ed_v2.csv` (57,500 synthetic visits, 365 days). These are pinned by
`tests/test_headline_regression.py`, so they cannot drift unnoticed.

| Result | This system | Baseline it is measured against | Margin |
|---|---|---|---|
| Wait-time MAE | **11.52 min** | 34.23 min — queue position × mean service time | **66.3% lower** |
| Interval coverage (0.90 target) | **0.8875** rolling conformal | 0.849 static split | **3.9 pp closer to nominal** |
| Arrivals forecast MAE | **2.356 /h** | 2.979 /h — seasonal-naive (last week, same hour) | **20.9% lower** |
| Cheapest feasible roster | **3 / 3 / 2 / 2 at 49,280** per week | 72 of 144 candidate plans were feasible | feasibility judged on the upper 95% bound |

Each baseline is the honest one for its task: the queue-position rule is what a charge
nurse does in their head, and seasonal-naive is the forecaster that is genuinely hard to
beat on hourly ED arrivals.

**Across ten regenerated datasets the methods hold and the roster does not.** The wait
model beat its baseline on all 10 seeds, the forecast beat seasonal-naive on all 10, and
rolling conformal coverage was 3.1× more stable than a static split. The simulation
validation gate **passed on 8 of 10** and refused to issue a staffing plan on the other
two. The cheapest plan cost **43,890 to 54,670** across the **8 seeds that produced one**
over **7 distinct rosters**, with the day shift at 3 in every single one. The staffing
*method* transfers; **3/3/2/2 at 49,280 is the reference dataset's answer**, not a
recommendation. Per-seed figures are in `artifacts/checkpoints/days_work.md`.

## Limitations

Stated here rather than buried, because these are the most important things about the
results.

1. **The data is synthetic.** Every number comes from data generated by a queue whose
   structure the models are then asked to recover. Agreement across seeds shows the
   pipeline is not over-fitted to one draw of that generator. It is **not evidence about
   any real emergency department**, and no claim here should be read as one.

2. **The staffing recommendation is partly circular.** The roster search is scored by a
   simulation that was calibrated to reproduce the same dataset the roster is being
   chosen for. It shows the *method* works; the specific roster is a property of the
   dataset. **3/3/2/2 at 49,280 is the reference dataset's answer, not a recommendation.**

3. **The validation gate has a known blind spot.** It compares marginal KPIs — per-acuity
   mean and p90 wait, length of stay, abandonment — so permuting waits **within** each
   acuity preserves every one of them exactly and passes. A dataset whose waits are
   completely independent of the queue would clear the gate. Catching it would need a
   check on the dependence itself, such as the correlation between queue length at
   arrival and realised wait. `test_within_acuity_decoupling_slips_past_the_gate` pins
   this and is written to fail loudly if the gate is ever strengthened.

4. **The gate refused a staffing plan on 2 of 10 regenerated datasets.** It passed on
   8 of 10. **Seed 8** was a rare-event tolerance artefact: ESI 3 abandonment missed a
   1.6% base rate by 1.2 percentage points, which is 72% in relative terms and
   clinically trivial. **Seed 10** was a genuine 8-minute miss on ESI 3 mean wait against
   an observed 34.4 minutes. A tolerance change that would clear seed 8 and leave seed 10
   failing is proposed in `days_work.md` and **deliberately not applied** — loosening a
   gate to make a failure go away is the move this design exists to prevent.

5. **The reinforcement-learning staffing agent is a negative result.** On a pre-declared
   60-episode budget it cost **17,832 more** than the fixed roster (95% CI 14,663 to
   21,002) and produced **more ESI 1-2 breaches than acting at random**. Reported as it
   stands; it was not retrained until it won. The budget — roughly five visits per table
   cell — is the obvious suspect, but that is a **hypothesis, not a defence**. It is also
   circular in the same way as (2): the agent learns a simulator calibrated to a
   generator, so a win would be evidence about the method alone.

6. **The resource extensions are not calibrated and cannot be.** Beds, nurses, imaging
   turnaround and bed-holding boarding are assumed, not measured: the data has no such
   columns, and neither would MIMIC-IV-ED. Read the *ranking* of levers; the minute
   counts are arbitrary. Every such output is labelled on screen and in its artifact.

7. **Real data would give a proxy wait, not a door-to-provider time.** MIMIC-IV-ED has
   **no first-provider-contact timestamp**. The two available proxies bracket the truth
   from opposite sides — first `vitalsign.charttime` under-estimates (charted at triage,
   before a clinician) and first `pyxis.charttime` over-estimates (follows a clinical
   decision, and only for patients given a drug, a biased subset). The adapter refuses to
   run without naming one, and every result from one is labelled **PROXY WAIT (NOT TRUE
   DOOR-TO-PROVIDER)**. `docs/real_data_readiness.md` sets out the governance,
   de-identification, retraining and re-validation that must happen first.

8. **The roster is configuration, and it describes the demo dataset.** Doctors are
   the only hard capacity constraint in the simulation, so every wait, scenario and
   staffing figure depends on the roster entered. A department with a different
   roster gets different numbers; the upload flow is where its own roster goes. The
   dashboard states this once, in **System status > Assumptions and limitations**,
   rather than as a warning box on each page that uses it -- four warnings before
   the first number teach a reader to skip all four.

9. **Other standing limits**, measured and recorded rather than discovered later:
   censoring bias in the wait models is downward and at least 7.8%; the classifier's
   false-negative rate for ESI 2 is 1.000 under a single pooled threshold; the
   treatment/boarding split is not identifiable from three timestamps; conformal coverage
   assumes exchangeability, which time-ordered blocks only approximate.

## Reproducibility

The dataset every headline number is computed on is reproducible from the generator in
this repository, by one command:

```powershell
python scripts\original_generator\generate_ed_data.py --days 365 --seed 42 --scale 9.7 --out <file>
```

That file and `data/raw/ed_v2.csv` are the same data. Verified with pandas rather than
asserted:

```python
import pandas as pd
a = pd.read_csv(r"data\raw\ed_v2.csv")
b = pd.read_csv(r"<file>")
a.equals(b)        # True
```

```
shapes            (57500, 10) == (57500, 10)
columns identical True
DataFrame.equals  True
```

The two files are **not byte-identical, and only because of line endings**: the committed
file is LF, `to_csv` on Windows writes CRLF, and the sizes differ by exactly 57,501 bytes
— one `\r` per line. They are equal after newline normalisation, and `.equals` is the
check that matters because it compares parsed values.

`scripts/original_generator/generate_ed_data.py` is the true generator and is never
edited. An older wrapper around `src/data/synthetic.py` exists in the history and must
**not** be used: its service times are total post-contact time where the true
generator's are physician-busy time, so the two do not describe the same department. A
seed-7 gate failure reported from the wrapper did not reproduce and has been withdrawn.

Everything else is deterministic given `seed` in `configs/default.yaml`: every stage
reads its inputs from disk, writes its outputs to disk, and can be re-run on its own.

## External validation

Two real datasets were obtained to test this project against data it did not
generate. Neither ships in `dist\ed-project-submission.zip`; both are one command
to fetch, and `data/external/README.md` records source, licence, retrieval date and
checksums.

### Real hourly ED arrivals (forecasting)

41,640 hourly arrival counts from the University of Iowa Hospitals and Clinics
emergency department, 2013-2018, from the R package **fastTS** (GPL >= 3). The
arrival forecaster was run on it **unchanged** -- same model class, same lag set
including the 168-hour seasonal lag, same rolling-origin design, same metrics, all
read from `configs/default.yaml`.

Over 26 rolling origins and 1,872 scored hours:

| | MAE | RMSE | sMAPE | WAPE |
|---|---|---|---|---|
| **This project's forecaster** | **2.025** | **2.611** | **37.7%** | **31.5%** |
| Seasonal-naive (168 h) | 2.751 | 3.602 | 51.4% | 42.9% |
| Mean of same hour, previous 4 weeks | 2.215 | 2.875 | 40.9% | 34.5% |

It wins at peak (3.04 against 3.95 and 3.24) and off peak (1.76 against 2.44 and
1.95), and its intervals cover at **0.898** against a 0.90 target -- better
calibrated on the real series than on the synthetic one, which under-covers at
0.8875. The gap to seasonal-naive is **26.4%** on real data against 20.9% on
synthetic, so the forecasting method transfers.

The run also found a defect: the project's nine configured holidays are all 2024
dates, so on 2013-2018 data `is_holiday` is constant and useless. **The model beat
both baselines with that feature accidentally disabled.** Same-hour temperature was
*not* used -- it is not known when a forecast is issued -- and a lagged version
correlates 0.31 with arrivals but only -0.03 with the model's residuals.

Full write-up: `artifacts/external_validation/uihc/report.md`.

### MIMIC-IV-ED demo (adapter check only)

The openly published demo subset, 222 ED stays, ODbL with attribution. **No model was
fitted on it and no model performance is reported from it**: 222 stays is far too
few, and a figure from it would be quoted later as though it were not.

What it did establish:

- The column map written from MIMIC's published schema, without any data in hand,
  maps the **real** columns. The adapter read all 222 stays through its own
  `adapt_real_dataset`.
- **One mapping was wrong and is now corrected.** `LEFT AGAINST MEDICAL ADVICE` was
  mapped to left-without-being-seen. Leaving against advice means a clinician saw and
  advised the patient, so it would have inflated the abandonment rate -- one of the
  quantities the simulation's validation gate is judged on.
- The two wait proxies bracket the truth from opposite sides, now measured rather
  than argued: first vitals median **2.0 min** (recorded at triage, so essentially
  the arrival time), first medication dispense median **118 min**, the dispense later
  in **80%** of stays by a median of 76 minutes. Every such figure is labelled
  **proxy wait (not true door-to-provider)**.
- **The queue state cannot be reconstructed from MIMIC-IV-ED, with or without
  credentials.** Dates are shifted per patient, which the demo makes visible: 222
  stays spanning 32,548 days at 0.01 stays per day. So the queue-state features --
  the ones that make the wait model beat its baseline threefold -- and the
  simulation's validation gate cannot be checked on it at all. Credentialed access
  would fix the sample size and nothing else on that list.

Full write-up: `artifacts/external_validation/mimic_demo/report.md`.

### What this does not claim

**No real-hospital performance is claimed for anything but the arrival forecast.** No
patient-level model touched real data: the UIHC series has no patients in it, and the
MIMIC demo was profiled rather than modelled. The wait model, the conformal
intervals on waits, the simulation and the staffing search remain validated only
against synthetic data.
